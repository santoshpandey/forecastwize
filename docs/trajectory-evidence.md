# Trajectory and evidence

Observational append-only traces of what the agent graph actually did.  
**LLMs do not forecast numbers.** Trajectory lines record decisions and
evidence IDs; yhat, WIS, and intervals come from deterministic Python.

This document describes the **implemented** persistence path after the
trajectory-observability phase. Forecasting, EXP-010, and the official
WIS comparison are unchanged by enabling persist.

## Architecture

Reuse the existing four layers. There is no second trajectory framework.

| Layer | Location | Role |
|---|---|---|
| Schema | `backend/app/evidence/trajectory.py` | Typed `TrajectoryRecord` (one JSONL line) |
| Logger | `backend/app/evidence/logger.py` | Redact secrets, strip raw series, hash input, append JSONL + artifact refs |
| Artifacts | `backend/app/evidence/artifacts.py` | Write-once `artifacts/{run_id}/A{step}-{sha8}.json` |
| Validator | `backend/app/evidence/trajectory_validator.py` | Deterministic JSONL / sequence / event-type checks |
| Agents | `backend/app/agents/*.py` | Build `TrajectoryStep`; persist when a path is provided |

The orchestrator owns one file per run/case. Child agents (Data Detective,
Forecast Strategist, Context Analyst, Verifier, Forecast Analyst) append to
**the same file** when official evaluation persist is on. They pass
`append_to_trajectory=True` so they do not truncate the parent file.

Standalone child tests still write their own JSONL and truncate that file.

## Event schema

Each persisted line is still a `TrajectoryRecord`. Additive fields:

| Field | Meaning |
|---|---|
| `event_id` | `{run_id}:{step_index}` assigned at write time |
| `case_id` | Evaluation case id (for example `001`) |
| `sequence` | Same as `step_index`; monotonically increasing in the file |
| `event_type` | Allowlisted observational type |
| `actor` | Agent or workflow identity |
| `payload` | Compact safe summary (no raw series) |
| `artifact_ref` | Pointer to a tool-output artifact when one was written |

Required reviewer fields from the original schema remain:
`run_id`, `agent_id`, `timestamp` (UTC ISO-8601), `input_state_hash`,
`input_summary`, `tool_invocation`, `tool_output_ref`, `decision`,
`evidence_ids`, `retry_number`, `status`, `error`, `agent_instruction`,
`next_step`, `final_result`.

Schema version: `TRAJECTORY_SCHEMA_VERSION` (`"1"`).

### Event types

`RUN_STARTED`, `RUN_COMPLETED`, `RUN_FAILED`,  
`AGENT_STARTED`, `AGENT_DECISION`, `AGENT_COMPLETED`,  
`TOOL_STARTED`, `TOOL_COMPLETED`, `TOOL_FAILED`,  
`BACKTEST_COMPLETED`, `ROBUSTNESS_ANALYZED`, `MODEL_VETOED`,
`MODEL_ELIGIBLE`, `MODEL_SELECTED`,  
`FORECAST_STARTED`, `FORECAST_COMPLETED`,  
`VERIFICATION_STARTED`, `VERIFICATION_COMPLETED`,  
`RETRY_REQUESTED`, `RETRY_STARTED`, `RETRY_COMPLETED`, `RETRY_NOT_REQUIRED`,  
`HUMAN_CHECKPOINT_CREATED`, `HUMAN_DECISION`.

Events are recorded only when the corresponding step actually runs.
The logger does not invent retries, human clicks, tool calls, or numbers.

## Storage location

Official catalog evaluation (12 real files, generated by actual
`python evaluation/run_agent.py` execution — not fixtures):

```text
evaluation/results/trajectories/<evaluation_run_id>/
  case_001.jsonl
  ...
  case_012.jsonl
  manifest.json
```

Cited official run: `evaluation/results/trajectories/agent-20260830T030413Z/`.

`python evaluation/run_agent.py` persists these by default. No debug flag
is required. Trajectories sit beside evaluation artifacts, not in
`backend/tests/fixtures/trajectories/` (those files are **test fixtures
only**). Interactive HITL: one real `HUMAN_DECISION` under
`evaluation/artifacts/human-demo/` — not part of the 12 catalog files.

Interactive API `POST /runs` still writes `data/api/trajectories/{run_id}.jsonl`
(gitignored runtime store).

## Official evaluation behavior

Default `persist_trajectory=True`. Each catalog case gets one JSONL file
containing orchestrator and child-agent events for that case.

`RUN_STARTED` includes safe metadata already available to the harness
(evaluation run id, selection policy, origin planning, git commit, library
pins). `RUN_COMPLETED` / `RUN_FAILED` records final status, selected model,
verification status, and retry count.

Numerical outputs are independent of persist. Same series, spec, seed, and
policy produce the same yhat / WIS with persist on or off.

## Human checkpoint semantics

**Evaluation `human_intervention_count` represents checkpoints opened, not
human decisions.**

Official catalog automation does **not** call `apply_human_checkpoint`.
Every WARN/FAIL-open gate is recorded as `HUMAN_CHECKPOINT_CREATED` with
`checkpoint_status=waiting_for_approval`. There is no fabricated
`HUMAN_DECISION` / `APPROVED` event.

A real `HUMAN_DECISION` is written only when a human uses the application
Accept / Reject / Review control (`apply_human_checkpoint`). That is a
separate interactive demo artifact, not part of automated evaluation.
See [human-in-the-loop-demo.md](human-in-the-loop-demo.md).

## Redaction

The logger redacts secret-like keys (`key`, `secret`, `token`, `password`,
`authorization`), `sk-…` tokens, and strips raw series keys (`values`,
`timestamps`, `residuals`, …). JSONL lines keep compact tool pointers;
full tool payloads live in artifacts after the same redaction.

Do not store API keys, authorization headers, private prompts, or
unnecessary raw dataset contents.

## How to inspect a trajectory

1. Open `evaluation/results/trajectories/<evaluation_run_id>/manifest.json`.
2. Open `case_012.jsonl` (or another case).
3. Walk `event_type` in `sequence` order.

Typical EXP-010 case 012 chain (actual events, not a script):

```text
RUN_STARTED
→ child diagnostics / tools
→ BACKTEST_COMPLETED
→ ROBUSTNESS_ANALYZED
→ MODEL_VETOED / MODEL_ELIGIBLE (per actual robustness rows)
→ MODEL_SELECTED
→ FORECAST_STARTED / FORECAST_COMPLETED
→ VERIFICATION_STARTED / VERIFICATION_COMPLETED
→ HUMAN_CHECKPOINT_CREATED (if a gate was opened)
→ RUN_COMPLETED
```

Retry events appear only if the graph actually retried. Cases with
`retry_number=0` may include `RETRY_NOT_REQUIRED` from the real accept
path. They must not include `RETRY_REQUESTED` unless a retry happened.

## How to validate trajectories

```text
from app.evidence.trajectory_validator import validate_trajectory_file
validate_trajectory_file(path, expected_case_id="012", expected_run_id="…")
```

Checks: valid JSONL, required fields, monotonically increasing sequence,
one `run_id` per file, matching `case_id`, unique `event_id`, allowlisted
`event_type`, no secret-like values, `RUN_COMPLETED` or `RUN_FAILED` on
completed files, no terminal events before `RUN_STARTED`.

The validator does **not** require `HUMAN_DECISION` or retry events.

## Fixture trajectories vs real trajectories

| Kind | Path | Meaning |
|---|---|---|
| Fixture | `backend/tests/fixtures/trajectories/*.jsonl` | Hand-checked-in schema examples for unit tests |
| Real catalog | `evaluation/results/trajectories/<run_id>/case_*.jsonl` | Direct output of `run_orchestrator` during official eval |
| API runtime | `data/api/trajectories/` | Interactive runs; gitignored |
| Human demo | `evaluation/artifacts/human-demo/<run-id>/` | One real Accept/Reject/Review; not official WIS |

Do not treat fixtures as official evaluation traces. Do not hand-edit
generated catalog JSONL.

## What is not in a trajectory

- Private chain-of-thought
- Holdout values (the graph never receives them)
- Raw training series
- Fabricated human approvals
- Fabricated retries
- Recalculated WIS (robustness events copy the deterministic tool result)
